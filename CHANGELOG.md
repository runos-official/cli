# Changelog

## v1.0.0-rc.8

Consolidated release candidate on top of v0.3.9. Supersedes the rc.1 through rc.7 series (those tags and releases were removed in favour of this single, cohesive entry). The CLI's IaC workflows, VCS deploy support, env-var split, regression-test scaffolding, and assorted hardening all ship in one tag. Install via `https://get.runos.com/cli.sh?release=v1.0.0-rc.8`.

### New

- **Apps as IaC**: `runos apps pull` / `apps diff` / `apps sync` round-trip an app's full configuration (yaml, env vars, secret files, manifest overrides) between cluster and disk. Pull supports bulk mode (`--all`), single-app mode, code-archive download (`--code` / `--code-version`), drift gates, and section-level diff reports. Sync pushes deltas via dedicated endpoints (PATCH /apps, env-vars, secret-files, overrides, requires).
- **Services as IaC**: `runos services pull` / `services diff` / `services sync` for postgresql, valkey, mysql, and any future service type the manifest exposes. Schema is manifest-driven (zero per-type code in the CLI); a new service type or new settable field on the API side flows through automatically after `runos manifest update`. Service yaml shape is desired-state only: `runos.service.<cid>.<type>.<sid>.yaml` contains exactly the fields the user can set; audit, derived, and operational fields the show response carries are filtered out automatically. Filename is convention; renames are tolerated via header-based lookup.
- **Apps integration with services IaC**: `apps_pull` cascades into pulling linked service yamls; `apps_sync` refuses `requires:` entries without an `id:` (provisioning is the service-yaml's job); `runos deploy` keeps the `requires.<alias>.class` shorthand and writes a service yaml on first-time provisioning.
- **PAT-based authentication**: `runos account api-keys add` / `list` / `show` / `update` / `revoke` for managing personal access tokens. The CLI consumes a PAT via `RUNOS_API_KEY` (plus `RUNOS_ACCOUNT_ID`, optional `RUNOS_API_URL`); when set, the CLI bypasses Firebase entirely. Headless CI runners need no `~/.runos/config.json` and no interactive `runos login`.
- **VCS deploys**: `runos deploy` dispatches on the app's `deployType`. CLI-deploy apps tarball the local source and upload (the classic flow). VCS-deploy apps send `{sha, configPath}` only; conductor and cluster agent pull source from the linked GitHub/GitLab integration at the SHA, build in-cluster, push, roll out. Flags: `--app <id>` for CI mode (no yaml on disk), `--sha` (defaults to `git rev-parse HEAD`), `--allow-dirty` (waives the dirty-tree refusal). The two modes never silently intermingle: passing `--sha` / `--allow-dirty` against a CLI-deploy app is a hard error, and passing `--app` against a CLI-deploy app is rejected after a server-side `deployType` lookup.
- **`configPath:` is the source of truth for a VCS yaml's repo location**: `runos deploy` auto-derives the repo-relative path of the local yaml (`git rev-parse --show-toplevel` + `filepath.Rel`) and sends it on every VCS deploy. Conductor persists it to the AppDocument, so subsequent CI deploys (`runos deploy --app <id> --sha <sha>` without a checkout) inherit the persisted value. Monorepos with apps under per-app subdirectories work without manual config. Explicit `configPath:` field in the yaml is honoured as an escape hatch.
- **Env vars split into Secret + ConfigMap**: alongside `.runos.<cid>.<id>.env` (sensitive, gitignored, K8s Secret), `runos deploy` / `apps pull` / `apps sync` / `apps diff` also handle `runos.<cid>.<id>.config.env` (plain, committed, K8s ConfigMap). Both flow into the pod via `envFrom` so app code reads them identically. A key may not appear in both files at once; conductor refuses the deploy with a 400 listing conflicts, and the CLI pre-flights the same check. Pull/sync/diff round-trip both sides independently.
- **`runos deploy --follow` streams per-step build logs**: the follow poller fetches new work-item log entries on each tick (cursor-paginated via `/jobs/:id/workitems/:id/logs`) and indents them under their parent step. GitHub Actions runs wrap streamed output in a `::group::` block and surface the public URL via `::notice::` after a successful deploy.
- **`runos follow <jobId>`**: blocking job-status follower with line-oriented output (one line per state change, no escape codes, no spinners, no repaints). Suitable for CI logs and AI consumers; exit code gates downstream pipeline steps. Exposed on MCP as `jobs_follow` (long-poll wrapper, blocks until terminal state).
- **Topic-driven MCP documentation**: the MCP read server requires the LLM to consume a minimum number of distinct topics (apps, services, api-keys, cicd, ...) before non-topic tools unlock, so AI assistants ground themselves in the workflow before executing it.
- **Service delete guard (409)**: `DELETE /services/<type>/<id>` returns a structured 409 listing dependent apps when any reference the service. The CLI renders this as a multi-line refusal naming each dependent and its alias, with reconcile guidance.
- **Empty-secret-env wipe gate**: `apps sync` refuses to push when the local secret-env file is empty (or carries only platform-injected names like `DATABASE_URL`) AND the server has user-set secret keys. Catches the fresh-checkout footgun where a gitignored secret file isn't on disk and the LLM/CI silently wipes prod secrets. The refusal names the keys that would be deleted. Pass `--allow-empty-secret-env` (CLI) / `allow_empty_secret_env=true` (MCP) when the wipe is intentional. The `--yes` confirm-skip flag does NOT waive this gate.
- **`apps pull --keep-env`**: opt-out from env file rewrites. Useful when the user has dev-only env edits they want to keep while still refreshing yaml, secret-files, and overrides. Stdout shows the kept paths so the user can run `apps diff` to see the divergence. Exposed on the MCP `apps_pull` tool as `keep_env`.
- **Pre-deploy drift gates**: `runos deploy` refuses when the local yaml has diverged from the running app on the server, and separately when newer CLI archives exist (someone deployed via console or CI between this directory's last pull/deploy and now). Both are fail-closed: an API failure refuses the deploy. Pass `--force` to override; the diff is shown either way.
- **TESTING.md**: testing philosophy and conventions. Pure-function regression tests on extracted helpers are the dominant pattern; the project explicitly does NOT write cobra-level subprocess tests or end-to-end tests against a live conductor.
- **`runos deploy` confirmation prompt**: a pre-deploy summary + `[y/N]` gate fires on both CLI and VCS deploy paths so a mistyped `runos deploy` (wrong directory, wrong cluster, wrong sha) doesn't silently kick off a build. Auto-skipped when stdin is not a terminal (CI, piped input). The `--yes` / `-y` flag is the explicit opt-out for TTY users who want the old behaviour. Summary lists app + cluster + account, plus the resolved build-context path (CLI) or short SHA + configPath (VCS).

### Improvements

- **Yaml is the source of truth for cluster id**: `apps sync` / `apps diff` / `apps pull <yaml>` / `apps pull` (auto-detect) / `apps list-previous-uploads` and `services sync` / `services diff` / `services pull <yaml>` read the cluster id from the yaml's `cid:` field. `--cid` and `RUNOS_CLUSTER_ID` become optional cross-check guards: passed values are validated against the yaml, mismatch refuses the operation. CI loops over committed yamls no longer need a default cluster set, no `--cid` per call. Commands without a local yaml to source from (`apps pull --all`, `apps pull --app-id`, `services pull --type+--service-id`) still require an explicit cluster id.
- **`apps pull` / `apps diff` correctly read `deployType`**: prior versions conflated provider name with deploy type and stored `github-arc` / `gitlab-runner` as `deployType`, producing perpetual drift on `apps diff` because the server emits `vcs`. Provider identity now flows via the `Integration` block alongside repo/branch metadata; `deployType` carries the canonical `cli` | `vcs` value with `integrationType` as a legacy fallback for older conductors.
- **Class-flap heads-up note on `apps diff`**: when the server stored `resourceRequirementClassId=custom` because cpu/memory/replicas overrides disagree with the named class's defaults, the diff surfaces a one-line note explaining the mechanic and how to round-trip cleanly.
- **MCP `deploy` tool gains VCS parameters**: `app`, `sha`, `allow_dirty`. Pre-validation stays in the CLI binary (one source of truth for the deployType branching rule) so the MCP shim only translates args.
- **MCP JSON Schema for object/array fields**: the manifest-driven tool generator emits `additionalProperties: {type: string}` for `object` fields and `items: {type: string}` for `array` fields. Strict-validating LLM clients (some Anthropic SDK tool wrappers) previously rejected the unannotated schemas. The `object` manifest type maps to JSON Schema `object` instead of being collapsed to `string`. `providerOptions` (domains_create / domains_update) drops `additionalProperties` so booleans round-trip natively.
- **MCP defensive JSON-string coercion**: when an MCP client ignores the declared field type and sends an `object` / `array` field as a JSON-encoded string, the executor decodes in-place so the wire body matches the manifest's declared type.
- **Tarball walker** unconditionally excludes RunOS-managed manifests (`runos*.yaml`, `runos.*/`, `overrides/`, dot-prefixed files) from every deploy archive, regardless of `.dockerignore`. Cross-cluster config can't bleed into a source upload.
- **`apps pull` writes a default `.dockerignore`** on first pull (skipped when present) covering the same exclusions so external Docker builders honour the same rules.
- **Multi-cluster project shape**: directory-per-app (`runos.<cid>.<id>/` subdirs with `sourceDir: ".."`) is the recommended shape for repos deploying to multiple clusters; `apps_pull` defaults to it and stamps `sourceDir` automatically.
- **CDN config schema**: `RemoteDomains` reads the canonical `api` field, falling back to the legacy `conductor` field for older payloads. Driven by an `APIURL()` resolver used everywhere the CDN environment is consumed.
- **Pre-deploy drift gate validates IDs as defence-in-depth**: app ID and cluster ID from the local yaml are charset-validated via `apps.ValidateIdentifier` before being joined into URLs, so a tampered yaml can't smuggle path components into API requests.
- **Build stamp on local builds**: `make local` stamps `dev-<utc-timestamp>` into the version string, so dev binaries are version-distinguishable in the wild. Stable releases continue to stamp the git tag.
- **`runos services sync` gains `--follow`**: was previously fire-and-forget with no opt-in to wait. Now matches the project-wide convention: prints `job: <id>` + `Follow rollout: runos follow <id>` hint by default; `--follow` (`-f`) streams the job to terminal status and exits non-zero on failure. Closes the silent-success gap that `apps sync` had pre-V12.
- **Documentation**: README and CLAUDE.md gain a deploy-verb section covering the deployType dispatch, the three cluster-id sources (flag, config, yaml), the SHA / dirty-tree gate, and the env-var Secret/ConfigMap split. CLAUDE.md links to TESTING.md from the testing section. CLAUDE.md gains a "Job-following convention" section that captures the opt-in `--follow` rule. README modernized: simplified quickstart (the default environment is auto-fetched on first run, no manual `runos config env` step), added Authentication and IaC sections, environment-variable table updated with `RUNOS_API_KEY` / `RUNOS_ACCOUNT_ID` for headless CI auth.
- **MCP integration: Roo Code target removed**. `runos mcp configure roo` no longer exists; supported targets are now Claude Code, Gemini CLI, OpenCode, and OpenAI Codex. The Roo-specific `.roo/mcp.json` writer and its handler are gone.
- **`runos deploy` prints the console URL on success**: the post-deploy summary now includes a `Console:` line linking directly to the app's `manage/<id>` page in the web console. Saves the user one tab and one mental URL stitch on every deploy.
- **`runos --version`**: top-level version flag wired (was previously only available via the `cli version` subcommand).
- **Deploy tarball excludes editor backups and the plain env file**: the upload walker drops `runos.yaml.bak` / `runos.*.yaml.backup` (created by user manual edits) and `runos.*.config.env` (per-cluster ConfigMap-backed env, supplied by the platform) so neither leaks into image builds. Mirrored in the default `.dockerignore` for users running external Docker tooling.
- **Default `.dockerignore` covers more conventional secret/junk directories**: `apps_pull`'s first-pull `.dockerignore` template now also excludes `.env` / `.env.*`, `.git/`, `.gitignore`, `secrets/` / `**/secrets/`, `**/.aws/`, `**/.ssh/`, editor backups (`*.bak`, `*~`, `.*.swp`), and common language ignores (`node_modules/`, `__pycache__/`, `.pytest_cache/`, `target/`). Preserves the previous RunOS-managed-files invariant (build context can never carry RunOS yamls / sidecars / overrides).
- **`apps sync` honours user-set secret-file `mountPath:`**: pre-fix, every secret file in the sync plan rendered with the synthetic `mountPath: /<filename>` even when the yaml's `secretFiles[*].mountPath` carried a real value. The mount path now sources from the manifest entry on adds and the server preserves the existing mount on updates.
- **`apps sync` plan now shows `requires:` drift inline**: pre-fix, the YAML diff section omitted requires-block changes even though they were on the wire (the patch sends the whole body). Plan now appends per-alias requires drift (`+`/`-` lines for type/id/config/env) so the user sees what they're confirming.
- **`apps sync` infers secret-file filename from `local:` when omitted**: a yaml entry with only `local: ./certs/web.pem` (no `filename:`) used to render as `+ (mount /)` in the plan and key the content map at the empty string (silently collapsing multiple entries). The basename is now inferred and propagated to both the manifest projection and the loaded content map.
- **`apps sync` env-conflict and platform-claimed errors render the actual filename**: pre-fix, when the yaml omitted `env:` / `secretEnv:` the conflict refusal printed an empty filename (`env-var keys appear in both  and `). Defaults are now resolved (`runos.<cid>.<id>.config.env` / `.runos.<cid>.<id>.env`) for the message.
- **`apps pull` JSON output carries a drift-resolution hint**: when one or more apps abort with local drift, the JSON summary gains a `hint` field explaining that post-deploy drift is expected (server-applied defaults like `replicas` / `resourceRequirementClassId`), not user work that would be lost. Surfaces inline to the LLM/MCP caller without forcing it to read the human-readable error stream. Also folded into the CLI-side error message.
- **`apps pull` no longer flags service yamls as ambiguous app candidates**: pre-fix, a directory containing `runos.yaml` plus a `runos.service.<cid>.<type>.<sid>.yaml` (the cascaded service yaml from class-shorthand provisioning) refused with "multiple yaml candidates" on auto-detect. The pull scanner now skips `runos.service.*` files since they're handled via `runos services` verbs.
- **`apps pull` round-trips health-check port and path independently**: pre-fix, both fields were gated on a non-empty `healthCheck` preset, so a yaml carrying `healthCheckPort: 8080` (with no `healthCheck:` key) lost the port on every pull. Each field now flows through independently, matching the conductor's omit-equals-clear desired-state semantics.
- **`apps sync --json` emits the dry-run plan as structured JSON**: opt-in via `--json` alongside `--dry-run`. CI pipelines can gate on yaml / env / secretFile / override change blocks without parsing the formatted plan output. Combining `--json` with apply (no `--dry-run`) is refused up-front since the post-apply jobIDs aren't part of the plan struct.
- **`runos deploy` writes post-deploy IaC artifacts on first deploy**: a fresh `runos deploy` (no prior `apps pull`) now writes the canonical `.dockerignore` template (idempotent: existing files are left untouched) and a placeholder `runos.<cid>.<id>.config.env` so the yaml's `env:` reference points at a real file. Pre-fix, a user who only ran `runos deploy` (the documented happy path) ended up with a yaml that referenced a non-existent file and had no `.dockerignore` to protect external `docker build` invocations from leaking RunOS-managed config into images. Errors print as warnings; the deploy itself doesn't roll back since the conductor side has already accepted the request.
- **`runos deploy --follow` rolls back the source-version sidecar on build failure**: pre-fix, every deploy wrote the new archive id to `.runos.<cid>.<id>.source-version` immediately, so a subsequent `--follow` build failure left the sidecar pointing at a UUID whose image was never produced. The next `runos deploy` (or drift gate) would treat the failure as the new baseline. The CLI now captures the prior recorded version, writes the new value, and on `--follow` failure restores the prior value (or removes the file when there was no prior baseline). Fire-and-forget deploys can't observe success/failure here so they keep the new value (still useful: `apps pull --code <uuid>` works because the archive uploaded).
- **Required positional fields on manifest-driven commands also accept `--<name>` flag form**: `runos apps status --id y2w1y` was previously rejected as `unknown flag` because the dynamic command builder only registered fields declared as non-positional. The builder now exposes every required string-typed positional as a `--<name>` flag too; the executor pulls the flag value into the body map when set; the missing-arg check honours either shape. Positional supply still wins when both are given. Error message updated to mention both forms (`missing required argument: id (or pass --id)`). `cid` is excluded from the auto-flag (every command whose endpoint contains `:cid` already gets a dedicated `--cid`).
- **Dynamic command leaves silence the usage block on runtime errors**: pre-fix, every API failure on a dynamic command (404 not-found, 409 dependents-refusal, transport errors, etc.) printed the full `--help` text after the diagnostic, drowning the actual error. Cobra `SilenceUsage: true` is now set on every leaf so the user sees the error and only the error. The error itself is still printed by cobra and propagates to the process exit code.
- **`runos apps logs` (and any log-shape array endpoint) streams one line per entry instead of breaking the table**: the manifest-driven response renderer now detects `[]{timestamp, message, ...}` arrays and prints `<timestamp> [<pod>] <message>` per line (mirroring `kubectl logs --timestamps --prefix`). The pre-fix wide-table render produced thousand-character rows that wrapped past the terminal and dwarfed every other column. `--json` keeps the full structured form for tooling that needs it.
- **Table cells summarise arrays-of-objects as `[N entries]`**: the `runos apps builds` output is the canonical case: the `logs` column carried an array of nested objects which the cell formatter inline-concatenated into ~1000-char `key=value, key=value; ...` runs that broke the table layout. Cells now render as `[3 entries]` (or `[1 entry]`) for any array-of-objects field; scalar arrays and primitives are unchanged. `--json` still exposes the full nested structure.
- **Manifest-driven commands no longer demand `cid` as a positional argument**: pre-fix, every dynamic command declared with `cid` as positional+required (most service writers, system-config endpoints) failed with a positional-missing error before the executor's flag/config-default fallback could resolve it. The builder now skips the positional-missing check for `cid` (the executor returns a single clear error if all three sources are empty) and renders the use line as `[cid]` so the help text doesn't mislead users into thinking the positional was the only path.

### Bug fixes

- **`OverrideSummary` accepts both `id` and `__docId` from the conductor's overrides response**: pre-fix, after the conductor route was updated to emit `id` (the 11b normalisation away from the Firestore-internal `__docId`), the CLI's struct still only read `__docId`. Post-normalisation responses left `OverrideSummary.ID` empty, which made `apps_diff` render `id: ""` in its overrides projection and `apps_sync` issue `DELETE .../overrides/` (trailing-empty path). The 11c/11d regression. The struct now defines a custom `UnmarshalJSON` that populates ID from whichever shape is present, so a CLI binary built against one conductor generation works against either. Regression test `TestService_ListOverrides_AcceptsPostNormalisationIDField` covers the post-normalisation shape.
- **`services diff --json` exits 2 on drift**: pre-fix, the `--json` branch returned early via `return emitJSON(diff)` before the exit-2 hook ran, so `services_diff --json` always exited 0 even when the report carried a drift status. CI gates that branched on the structured signal silently passed. The exit hook now runs after both human and JSON paths, matching `apps_diff`'s contract verbatim. The MCP wrapper still translates exit 2 into a successful drift-report payload.
- **`apps sync --redact-secrets` covers plain env too**: pre-fix, the redact flag only redacted secret-side env values; a third-party API key accidentally committed to the plain `config.env` (technically disallowed but easy to do by mistake) leaked verbatim into the plan output and from there into LLM context. The flag's stated contract is "keep secrets out of LLM context", so plain env values are now redacted under the same flag. Cost: a slightly less informative plan when the user opts in. Benefit: the LLM driving the sync never sees a value it doesn't strictly need.
- **`runos deploy` code-drift gate fails closed when the recorded source version isn't on the server**: pre-fix, the gate silently skipped (and printed a warning) when the local `.source-version` referenced an archive id that was no longer in the server's archive list. That made the gate trivially bypassable: hand-edit `.source-version` to garbage and the gate goes quiet. The fix refuses the deploy unless `--force` is passed, and renders a multi-line guide with `runos apps list-previous-uploads` / `runos apps pull --code --force` reconcile commands. With `--force`, the prior warn-and-proceed behaviour is preserved.
- **Plain-side platform-claimed env vars refused on `runos deploy` and `apps sync`**: pre-fix, a `DATABASE_URL=...` (or any name claimed by a `requires.<alias>.env` mapping) committed to the plain `runos.<cid>.<id>.config.env` file was silently ignored at runtime (the requires-merge wins) but happily persisted into Git history. The CLI now refuses on the deploy and sync paths with the offending names and their claiming aliases listed; the user moves them to the secret-side file (where the platform writes its own value on every deploy and the merge re-runs harmlessly). The secret-side equivalent stays unrefused since apps_pull legitimately writes those values there and the merge re-runs on every deploy.
- **`runos config get` no longer shadowed by a duplicate dynamic `config get`**: pre-fix, the manifest's system-config namespace and the static CLI-config command both rendered as top-level `config` entries in `runos --help`, and the merged tree attached two `get` leaves to the same parent (cobra picked one nondeterministically). The dynamic command builder now skips a child whose name is already present on the merged parent, and `cmd/root.go` registers `configCmd` and `deployCmd` as existing so the merge happens at the right node. Fixes both the duplicated `--help` listing and the dispatch ambiguity.
- **`runos cli version-check` no longer reports a phantom update**: pre-fix, the bare CLI invocation (without `--version` / `--os`) sent empty strings to the manifest endpoint, which produced a misleading `updateAvailable: true` plus an alarming sentinel in `releaseNotes`. The dynacmd executor now auto-injects the running binary's version (`version.Version`) and `runtime.GOOS` when those fields are unset, mirroring the MCP wrapper. Manual overrides via `--version` / `--os` still win.
- **`services sync` CREATE plan no longer wipes non-secret values from plan output**: pre-fix, `--redact-secrets` (always set on the MCP path) replaced every value with `<redacted>` indiscriminately, so the user was asked to confirm `name: <redacted>`, `resourceRequirementClassId: <redacted>`, `storageMb: <redacted>`. Redaction is now scoped to keys whose names look sensitive (password, token, secret, apiKey, credentials, privateKey). Service config fields stay legible. Plan title also renders `<new>` for CREATE plans instead of leaving the id slot blank.
- **`services sync` CREATE no longer poisons the local yaml's `id:` field with the OSID**: pre-fix, the conductor's create response carries the long-form `osid` (e.g. `minio-v2k5k`) and the CLI fell back to it verbatim when `id` was missing on the response. The yaml's `id:` field expects the bare 5-char id, so subsequent diff/pull/sync 404'd ("Service not found") until the user fixed it by hand. The fallback now strips the `<type>-` prefix when present so the yaml stays consistent.
- **`services sync` CREATE accepts add-endpoint flags (e.g. `exposeS3On443`)**: pre-fix, `AddInputFieldNames` only walked the manifest's fields list and missed boolean flags, so valid create-time options were spuriously refused as "not patchable on this service type". Flags are now folded into the same allow-list (the dynacmd executor splits them on the wire). Refusal wording on CREATE also no longer says "patchable" since there's no service yet to patch; it now says "not accepted by this service type's add endpoint".
- **`apps diff` / `apps sync` honour default env paths when the yaml omits the field** (V3): pre-fix, an app whose yaml had no `env:` (or `secretEnv:`) field but had a file at the documented default path (`runos.<cid>.<id>.config.env` / `.runos.<cid>.<id>.env`) was silently reported `in_sync` and the file's contents never made it to the server on a sync. `BuildDiffReport` now computes the env diff sections whenever EITHER side has content (server vars OR a local file at the resolved path), and `LoadLocalEnv` falls back to the caller-supplied default when the yaml ref is empty. Symmetric with what `apps pull` writes by default.
- **Job-following convention standardised across all commands**: every command that produces a server-side job defaults to fire-and-forget; pass `--follow` (`-f` where free) to wait for terminal status. No auto-follow based on TTY, CI env vars, or any implicit signal. Applies to `runos deploy`, `runos apps sync`, `runos services sync`, and every manifest-driven command whose response shape declares a `jobId` (auto-wired in `internal/dynacmd/builder.go`). Without `--follow`, the command prints the job id and a `Follow rollout: runos follow <id>` hint. With `--follow`, it streams progress via the shared follow path and exits non-zero on terminal `failed`. Documented in `CLAUDE.md` under "Job-following convention" so the rule is canonical.
- **CLI manifest bootstrap on first run** (V6): pre-fix, fresh CI installs hit an inconsistency: `runos deploy` (statically defined) soft-warned about the missing manifest and continued, but `runos services sync` / `runos apps pull` (manifest-driven) hard-failed with "Error: load manifest...". Same root cause, different blocking behaviour. `cmd/root.go`'s `PersistentPreRunE` now runs a manifest fetch in the same shape as the existing `config.InitFromRemote` first-run bootstrap. Skip-list: `version` / `help` / `config` / `update` / `manifest *` (avoids surprising network calls and double-fetch on `runos manifest update`).
- **`apps pull` auto-updates server-side `configPath` on mismatch** (V2 / V14): pre-fix, pulling a VCS-deploy app to the canonical `runos.<cid>.<id>.yaml` naming with no awareness of where the AppDocument's `configPath` said the yaml lives would silently set up the next VCS deploy to fail at the cluster-agent's yaml-fetch step. Pull now PATCHes the server's `configPath` to match the new local layout (skipping CLI-deploy apps, and skipping when the local path can't be repo-relative-resolved because we're not in a git checkout). The action is reported on the JSON pull response as `configPathUpdated: {from, to}` so the MCP wrapper carries the structured signal through automatically. Falls back to the legacy stderr warning on PATCH failure. `--no-configpath-update` opts out for the rare case the user wants pull to leave server state alone.
- **`sourceDir` and `dockerfile` round-trip through the AppDocument** (V13): pre-fix, the local yaml's `sourceDir` (build context) and `dockerfile` (Dockerfile path within sourceDir) never reached the server, so a fresh checkout that ran `apps pull` got an incomplete yaml: every monorepo app had to manually re-add these fields after every clone or filename rename, and a missing `sourceDir` made the next build die at `failed to read dockerfile: open Dockerfile: no such file or directory`. `BuildPulledApp` now extracts both fields from the API response and writes them back via `apps pull`; `computeYAMLPatch` / `buildFullYAMLBody` push them on `apps sync`; `apps diff` reports drift on either field like other partial-update fields. Both fields apply to CLI and VCS deploys and round-trip uniformly. Edits limited to `configPath` / `sourceDir` / `dockerfile` (any combination) hit the conductor's sync fast-path (no redeploy). Local yaml values still win over server values on pull so manual edits survive re-pulls. Conductor counterpart in this release: `patchAppBuildMetadata` + `validateBuildMetadata` (lexical path containment).
- **`apps pull` recomputes sourceDir client-side during configPath auto-update** (V19): pre-fix, V14/V17's auto-update hook PATCHed `{configPath: <new>}` alone, and conductor's V13/V16 lexical containment validator merged with the stored `sourceDir`. When the new configPath dir was shallower than the old one, the merge often escaped the repo root (canonical case: relocating from `infra/runos/apps/runos.yaml` to `tmp/runos.yaml` while sourceDir stayed `../../../apps/frontend` → merged path `../../apps/frontend` → 400). V18 surfaced the failure structurally; V19 prevents it. The CLI now pre-computes a sourceDir relative to the new configPath dir that preserves the absolute repo target the existing pair pointed at, applies it to `serverState.SourceDir` BEFORE the local yaml write so the on-disk yaml is coherent at the new layout, and includes the same value in the PATCH so server and local stay in sync. Pure helper `apps.RelocateSourceDir` returns "" when no recompute is needed (no relocation, default sourceDir, naive merge stays in repo) or when the existing pair already escapes (legacy bad state); the V18 error-surface stays as the fallback in that case. `dockerfile` doesn't need touching: it's path-relative to `sourceDir`, and the preserved absolute sourceDir target keeps the dockerfile resolution chain consistent. Briefed initially as a conductor change (structured 400 with suggested replacement values); conductor team pushed back that path math belongs client-side and the half-step toward typed-error responses set the wrong API precedent. Resolved by lifting the math into the CLI with no conductor change and no API surface growth. Regression test `TestRelocateSourceDir` covers the V18 trigger, no-op cases (same-dir, default sourceDir, in-repo merge), legacy bad state, and edge inputs (10 cases).
- **`apps pull` surfaces configPath auto-update failures structurally** (V18): pre-fix, when the V14 auto-update PATCH was rejected (canonical case: conductor's V13/V16 lexical-containment validator refusing the new configPath because the stored sourceDir would escape the repo root once configPath moves to a shallower dir; also any transport / auth / 5xx error), the failure was stderr-only. MCP-driven LLMs got a pulled-app entry with no `configPathUpdated` and no error field, indistinguishable from a successful no-op pull. Fix adds a sibling `configPathUpdateError: { from, to, error }` field on the per-app entry, populated whenever `svc.UpdateApp` returns an error during the auto-update branch. The `error` field carries the conductor's response verbatim (or the transport error string), so callers see the same actionable message direct-CLI users get on stderr. Mutually exclusive with `configPathUpdated` in practice (one PATCH attempt, one outcome). MCP wrapper unchanged: the JSON passthrough at `internal/mcp/apps.go` carries the new field automatically. Deliberately did NOT add a CLI-side pre-flight that re-implements the conductor's lexical validator: the duplicate logic would silently diverge if the conductor's rules tighten or loosen, and surfacing the conductor's error verbatim gives the LLM the same actionable message anyway. Conductor stays the authoritative validator.
- **`apps pull` configPath auto-update fires regardless of CLI cwd** (V17): pre-fix, the V14 hook silently no-op'd when `apps pull` was invoked from a CWD outside the pull target's git repo, the canonical case being MCP-driven pulls where the CLI subprocess inherits the MCP host's CWD (typically the user's editor project, not `--out`). `vcsRepoRelPath` resolved git context from the process CWD via `git rev-parse --show-toplevel`, returned the wrong root (or errored), and the local-vs-server configPath comparison fell into the `localRepoRelPath == ""` skip branch. Fix anchors git resolution at the yaml's directory using new `git.IsRepoAt` / `git.RepoRootAt` helpers (`git -C <yamlDir>`), absolutizes `--out` in `resolvePullPlan` so `filepath.Dir(yamlRes.Path)` is unambiguous, and extracts the path math into a pure `apps.RepoRelPath` helper covered by `TestRepoRelPath`. CLI-deploy apps stay unaffected: `DecideConfigPathAction` short-circuits on `deployType != "vcs"` regardless of the repo-relative-path value.
- **Parallel `apps pull` no longer races for `runos.yaml`** (V1): pre-fix, fanning out N concurrent `runos apps pull --app-id <id> --out <dir>` calls (the LLM/CI shape) into a shared empty target dir would leave one outlier at the canonical `runos.yaml` and N-1 at the per-app suffixed `runos.<cid>.<id>.yaml`. Whichever pull won the race claimed the canonical slot. Fixed by routing the `id-flat` pull mode through new `apps.SaveYAMLSuffixed`, which writes straight to the suffixed leaf without consulting the directory state, so concurrent callers each land at their own deterministic path with no contention. Single-app modes (yaml-positional, bulk, id-subdir) keep using `SaveYAML` so `runos.yaml` is preserved on a re-pull where there's no race possible.
- **`apps pull` and `runos deploy` provisioning respect existing service yamls anywhere in the repo** (V4): pre-fix, projects that organise infra as `infra/runos/apps/` + `infra/runos/services/` (apps and services in sibling dirs) saw both `apps_pull`'s services cascade AND deploy's class-shorthand first-time provisioning re-create duplicate service yamls next to the app yaml because the lookup only checked the app's own directory. Both call sites now share new `services.ExistingServiceYamlPath`, which scans the entire git repo root via `FindByIDInTree` and skips the write when a matching service yaml exists anywhere reachable. Heavy dirs (`.git`, `node_modules`, `vendor`, `.runos`) are skipped during the scan to keep it cheap. Outside a git checkout the lookup falls back to a single-dir `FindByID`, preserving the single-app-at-root behaviour. `--no-services` continues to opt the cascade out entirely.
- **`apps sync` blocks per emitted job when `--follow` is set** (V12, CLI half): each step's `(job <id>)` line previously printed the moment the conductor accepted the API call, so silent cluster-side failures (`kubectl patch` on a missing configmap was the canonical case) silently completed the CLI with exit 0. With `--follow`, sync now waits for each step's terminal status, prints `FAILED: <conductor.error>` on failure, and aborts the rest of the plan with non-zero exit. Without `--follow`, sync stays fire-and-forget and prints the trailing `runos follow <id>` hints. The conductor half (`patchConfigMapData` / `patchSecretData` create-on-missing-then-patch) shipped separately.
- **`runos deploy --follow` and `runos follow <jobId>` accept `RUNOS_API_KEY`** (V11): `internal/jobs/service.go:getAuthToken` and `internal/update/updater.go:getAuthToken` were bypassing `auth.ResolveToken` and hard-requiring `cfg.Firebase`, so PAT-only CI hit `authentication required: run 'runos login' first` on the job-progress streaming endpoints (the deploy POST itself worked because it correctly used `auth.ResolveToken`). Both delegate to `auth.ResolveToken` now; the auth contract matches every other API-touching surface in the CLI.
- **`runos deploy` env merge flipped to local-wins**: the pre-deploy sync used to refuse on any same-key-different-value conflict between local and server, blocking the dominant path (every version bump, every flag flip) until the user manually reconciled. The merge now copies the local file verbatim and adds only server-only keys; the deploy that follows pushes local up and replaces the server-side env in full.
- **`runos deploy` skips env file write when the merge is a no-op**: prevents the inverse footgun where a fresh checkout with no local env file would produce a strict no-op merge, the file would never materialise, and the subsequent deploy body would carry an empty `customEnvVars` map that conductor interpreted as "user wants empty ConfigMap" and wiped server env on every deploy.
- **`apps sync` override delete now removes the orphan local file**: the delete op carries `LocalLeaf` (the leaf filename inside `appDir/overrides/` that pull would have written for this override). Apply unlinks the local file alongside the server delete; previously deleting an override server-side left the local file orphaned.
- **`apps diff` no longer flags local-only `sourceDir` as drift forever** (superseded by V13): pre-V13, the diff engine stripped top-level `sourceDir:` lines from local bytes before comparison since `sourceDir` was a CLI-only field that never reached conductor. V13 round-trips `sourceDir` and `dockerfile` through the AppDocument, so the strip is no longer needed and was removed; field-level drift on either now surfaces normally on `apps diff` and reconciles via `apps sync`.
- **`apps pull` preserves `resourceRequirementClassId: "custom"`**: prior versions rewrote the literal string `"custom"` as empty during pull, fighting with `apps show` (which surfaced the literal from the server's `resolveRRC` synthesis). Pull preserves the literal so `apps_show` and `apps_pull` return symmetric views.
- **`apps sync` no longer renders preserve-sentinels as drift**: `clusterDomainId`, `resourceRequirementClassId`, and `replicas` are partial-update fields on conductor's PATCH endpoint (omitted local value means "preserve server value", not "clear / set to zero"). Drift reporting mirrors the wire body's omit logic.
- **`apps diff` exits 2 on drift**: structured exit code so CI can branch on "config drift detected" without parsing stdout. Exit 0 = in sync; exit 2 = drift; any other non-zero = real failure.
- **MCP `apps_diff` translates exit code 2 to success**: drift is the structured signal `apps_diff` returns, not a failure mode. The MCP wrapper hands the drift report back to the LLM caller as a normal text payload. The translation lives in a pure helper (`interpretAppsCommandResult`) tested directly with synthesized `*exec.ExitError`. CI users still see the non-zero exit at the CLI layer.
- **`services sync` class-only swap no longer flips class to "custom"**: the PATCH body is drift-only (`computeDriftPatch`): fields whose local value matches the server are omitted, so a class-only swap touches only the class field and conductor's `resolveRRC` doesn't flip class to "custom" from materialised cpu/memory baselines.
- **`services pull` no longer projects class-derived cpu/memory/replica fields when a real resource class is stored**: now that the API manifest declares those fields as settable on `services/<type>/{id}/update`, the manifest-driven pull was projecting them into every yaml regardless of the stored class. The CLI mirrors the apps_pull preset-wins gate: real class → strip the five derived fields; `custom` (or empty / legacy) → keep them as the user-owned source of truth.
- **`apps pull` user-set secret env count no longer double-counts platform-injected keys**: `envVarCount` in the pull JSON summary used to sum plain + secret without filtering. Now `envVarCount` matches `apps_env-vars` keys exactly, and `secretEnvVarCount` reflects user-set secret keys only.
- **`apps diff` `--redact-secrets` covers the secret env section**: values in the `SecretEnv` `SectionDiff` are redacted in the unified-diff output by the same flag that redacts `.env` content. The MCP `apps_diff` tool keeps passing `--redact-secrets`.
- **Windows build**: `syscall.O_NOFOLLOW` (used in `apps_pull`'s symlink-refusal write path) doesn't exist on Windows. Replaced with a build-tagged constant: protection is preserved on Unix; the flag is a no-op on Windows where the equivalent OS-level guarantee isn't available.
- **`runos deploy` auto-detects pulled yaml in cwd when no `-c` and no `runos.yaml`** (I15-A): pre-fix, deploy emitted a cryptic "runos.yaml not found at <path>" while `apps diff` already had a candidate-enumeration scanner. Deploy now scans the cwd for `runos.<cid>.<id>.yaml` (both `apps.YAMLScan.Valid` and `.Partial`), auto-picks a unique hit, and surfaces a candidate list mirroring `apps diff`'s message on multi-hit. Zero-hit falls through to the original LoadConfig error.
- **Manifest-driven commands accept yaml body via stdin (`-f -`)** (I15-B): pre-fix, the pre-network required-field gate and the RunE body collector each opened stdin independently, so the first reader drained the pipe and downstream gates fired "missing required field". `loadYAMLFile` now sync.Once-caches a 10MiB-capped `io.LimitReader(os.Stdin, ...)` read so all three call sites see the same parsed body.
- **`--json` error envelopes forward unknown top-level fields verbatim** (I15-C): pre-fix, `BuildAPIErrorEnvelope` extracted only `error` from the inner body and synthesised `statusCode`, dropping any structured detail the server emitted (e.g. an `upstream: {provider, status, body}` block from a future cloudflare-style error shape). Forward-compat pass-through copies every top-level inner-body key into the envelope, with `error` (overridden from the inner string) and `statusCode` (authoritative from the typed `*APIError`) protected. Future conductor-side error-detail keys surface to MCP/JSON consumers without a CLI release.
- **MCP executor strips `"<cid> (Cluster Name)"` display label off body-field cids** (I16-C): pre-fix, `extractCID` ran for URL-path substitution but the un-stripped value remained in `args["cid"]`, so account-scoped POSTs that carry `cid` as a body field (canonical case: `cluster-domains/add` against `/:aid/cluster-domains`) sent the literal display label to the conductor. Conductor accepted it unchecked and the downstream CP lookup against the bogus id surfaced as a misleading "no control-plane nodes are registered" error. `Execute` now mirrors the stripped value back into `args["cid"]` before `buildBody` runs. Conductor 12.4.0's server-side `clusterRepository.findById` validation + 12.5.0's `normalizeCid` accept-both-forms helper stand as defense in depth.
- **MCP cid descriptions no longer prompt models toward the parenthesised display form**: with conductor 12.5.0 normalising both `"mycluster2"` and `"mycluster2 (Cluster-2 mycluster2)"` and CLI R8 stripping the suffix client-side, the verbose `"format 'xyz (Cluster Name)'"` guidance in MCP tool descriptions was actively pushing models into a form with no remaining functional purpose. Descriptions across `apps_pull` / `apps_diff` / `apps_sync` / `apps_list_previous_uploads` / `services_pull` / `services_diff` / `services_sync` / `deploy` / the generic `:cid`-endpoint wrapper now read simply `"Cluster ID. Defaults to the configured default cluster."` (or `"Cluster ID. Cross-checked against the yaml's own cid field."`).
- **MCP `cluster-domains_show id=runos` returns the actionable synthetic-runos redirect** (I17-A): pre-fix, the cobra/dynacmd path intercepted `cluster-domains show --id runos` with `"\`runos\` is a synthetic per-cluster cluster-domain; use \`runos cluster-domains list-by-cluster --cid <cid>\`..."` (I11-W) but the MCP executor ran past that gate, so MCP/LLM consumers got a bare conductor 404. The MCP executor now mirrors the gate with an MCP-tool-name-appropriate phrasing (`cluster-domains_list-by-cluster` tool instead of the cobra invocation).
- **Service-type logs gain `--follow` and duration `--since` parity with `apps logs`** (I17-F): pre-fix, the iter-14 I14-E (`apps logs --follow` poll-2s stream) and I14-F (`apps logs --since 5m` duration-string parsing) fixes landed on `apps/logs` only. Under `--follow + --json`, per-step job progress also routes to stderr via the new `FollowJobWithServiceToWriter`.

## v0.3.9

### New

- **Empty-secret-env wipe gate**: `apps sync` now refuses to push when the local secret-env file is empty (or carries only platform-injected names like `DATABASE_URL`) AND the server has user-set secret keys. Catches the fresh-checkout footgun where a gitignored secret file isn't on disk and the LLM/CI silently wipes prod secrets. The refusal names the keys that would be deleted. Pass `--allow-empty-secret-env` (CLI) / `allow_empty_secret_env=true` (MCP) when the wipe is intentional. The `--yes` confirm-skip flag does NOT waive this gate, since `--yes` is "skip the prompt for the safe case" and not "I'm OK with destructive ops".

Useful when the user has dev-only env edits they want to keep while still refreshing yaml, secret-files, and overrides. Stdout shows the kept paths so the user knows nothing was rewritten and can run `apps diff` to see the divergence. Exposed on the MCP `apps_pull` tool as `keep_env`.
- **`jobs_follow` MCP tool**: long-poll streaming wrapper around `runos follow <jobId>`. Blocks until the job reaches a terminal state (success / failed / cancelled) or the 10-minute subprocess timeout fires, then returns the full streamed work-item log + final status as a single text payload. The canonical "wait until done" verb for orchestrations: cheaper than polling `jobs_show` in a loop and doesn't burn the LLM's prompt cache. Read-only.
- **TESTING.md**: testing philosophy, conventions, patterns, and a running list of regression tests by fix. The bar: a test earns its place if a future change that re-introduces a known bug would fail it. Pure-function regression tests on extracted helpers are the dominant pattern; we explicitly do NOT write cobra-level subprocess tests or end-to-end tests against a live conductor.

- **`apps sync` override delete now removes the orphan local file**: the delete op carries `LocalLeaf` (the leaf filename inside `appDir/overrides/` that pull would have written for this override, derived via `OverrideFilenames` over the full server list so collision-disambiguated names match what pull wrote). Apply unlinks the local file alongside the server delete; previously deleting an override server-side left the local file orphaned and the next pull-then-sync would re-create it.
- **`apps diff` no longer flags local-only `sourceDir` as drift forever**: `sourceDir` is a CLI-only field (build-context resolution for `runos deploy`) that never reaches conductor and never appears in server-rendered yaml. The diff engine strips top-level `sourceDir:` lines from local bytes before comparison. Pulled yamls that include `sourceDir: ..` (the directory-per-app shape) no longer report drift on every diff.
- **`apps pull` preserves `resourceRequirementClassId: "custom"`**: prior versions rewrote the literal string `"custom"` as empty during pull, which fought with `apps show` (which surfaced `resourceRequirementClassId="custom"` from the server's `resolveRRC` synthesis). Pull now preserves the literal so `apps_show` and `apps_pull` return symmetric views; materialised cpu/memory fields are still emitted alongside, since `"custom"` by itself carries no values.
- **`apps sync` no longer renders preserve-sentinels as drift**: `clusterDomainId`, `resourceRequirementClassId`, and `replicas` are partial-update fields on the conductor's PATCH endpoint (omitted local value means "preserve server value", not "clear / set to zero"). The wire-body builder already omitted these correctly, but the dry-run plan was rendering alarming `replicas: 1 -> replicas: 0` lines for every yaml that omitted them, scaring users into refusing the (harmless) sync. Drift reporting now mirrors the wire body's omit logic.
- **`apps diff` exits 2 on drift**: structured exit code so CI can branch on "config drift detected" without parsing stdout. Exit 0 = in sync; exit 2 = drift; any other non-zero = real failure.
- **MCP `apps_diff` translates exit code 2 to success**: drift is the structured signal `apps_diff` returns, not a failure mode. The MCP wrapper now hands the drift report back to the LLM caller as a normal text payload instead of wrapping it in a red error block. The translation lives in a pure helper (`interpretAppsCommandResult`) tested directly with synthesized `*exec.ExitError`. CI users still see the non-zero exit at the CLI layer.
- **`services sync` class-only swap no longer flips class to "custom"**: pulling a service materialises the active class's cpu/memory baseline into the local yaml. Editing only the class line and syncing was sending the OLD baseline cpu/memory in the wire body; conductor's `resolveRRC` interpreted those as overrides against the NEW class baseline and flipped class to "custom". The PATCH body is now drift-only (`computeDriftPatch`): fields whose local value matches the server are omitted, so a class-only swap touches only the class field.
- **`apps pull` user-set secret env count no longer double-counts platform-injected keys**: `envVarCount` in the pull JSON summary used to sum plain + secret without filtering, which inflated the count and disagreed with what the `apps_env-vars` endpoint returned. Now `envVarCount` matches `apps_env-vars` keys exactly, and a separate `secretEnvVarCount` reflects user-set secret keys only (platform-injected keys claimed by `requires.<alias>.env` mappings are filtered out of the user-facing count).
- **MCP `domains_create` / `domains_update` `providerOptions` round-trips booleans**: the manifest-driven schema generator was emitting `additionalProperties: {type: string}` for `object` fields, which forced LLMs to send `proxy: "true"` (string) into a field that `domains_list` returned as `proxy: true` (bool). The conductor's `normalizeProviderOptions` was coercing back, but the schema mismatch was visibly confusing. The generator now drops the `additionalProperties` constraint specifically for `providerOptions` so booleans round-trip natively.

### Improvements

- **`apps sync` drops the "remove these dead-config keys" advisory**: previous versions emitted a "the platform injects these at runtime" note when the local secret-env file contained names claimed by `requires.<alias>.env` mappings (DATABASE_URL, REDIS_URL, etc.). The advice was wrong-headed: those keys are written to the local file by `apps pull` so it matches the K8s Secret, and the pre-deploy merge re-introduces them on every deploy. Removing them makes local LESS accurate, not more. The note and its formatter are gone; the underlying detection helper is retained as `FindServerInjectedEnvCollisions` and now used only to filter `runos deploy`'s "got merged back" warning so the user isn't pestered about keys that re-appear by design.
- **Documentation**: CLAUDE.md links to TESTING.md from the testing section. New tests added across `internal/apps/sync_test.go`, `internal/apps/pull_test.go`, `internal/apps/diff_test.go`, `internal/mcp/apps_test.go`, `cmd/deploy_test.go`, `internal/services/sync_test.go` covering each fix above as a regression test.

## v1.0.0-rc.6

Adds VCS deploys, splits env vars into Secret + ConfigMap, and brings live build-log streaming to `runos deploy --follow`. Install via `https://get.runos.com/cli.sh?release=v1.0.0-rc.6`.

### New

- **VCS deploys**: `runos deploy` now dispatches on the app's `deployType`. CLI-deploy apps still tarball the local source and upload (unchanged). VCS-deploy apps send `{sha, configPath}` only; the conductor and cluster agent pull source from the linked GitHub/GitLab integration at the SHA, build in-cluster, push, and roll out. New flags: `--app <id>` for CI mode (no yaml on disk), `--sha` (defaults to `git rev-parse HEAD`), `--allow-dirty` (waives the dirty-tree refusal). The two modes never silently intermingle: passing `--sha` / `--allow-dirty` against a CLI-deploy app is a hard error, and passing `--app` against a CLI-deploy app is rejected after a server-side `deployType` lookup.
- **`configPath:` is the source of truth for a VCS yaml's repo location**: `runos deploy` auto-derives the repo-relative path of the local yaml (`git rev-parse --show-toplevel` + `filepath.Rel`) and sends it on every VCS deploy. Conductor persists it to the AppDocument, so subsequent CI deploys (`runos deploy --app <id> --sha <sha>` without a checkout) inherit the persisted value. Monorepos with apps under per-app subdirectories (`apps/billing/runos.dev.yaml`) work without manual config. Explicit `configPath:` field in the yaml is still honoured as the escape hatch for non-standard layouts.
- **Env vars split into Secret + ConfigMap**: alongside the existing `.runos.<cid>.<id>.env` (sensitive, gitignored, K8s Secret), `runos deploy` / `apps pull` / `apps sync` / `apps diff` now also handle `runos.<cid>.<id>.config.env` (plain, committed, K8s ConfigMap). Both flow into the pod via `envFrom` so app code reads them identically. A key may not appear in both files at once; conductor refuses the deploy with a 400 listing conflicts, and the CLI pre-flights the same check. Pull/sync/diff round-trip both sides independently.
- **`runos deploy --follow` streams per-step build logs**: the follow poller now fetches new work-item log entries on each tick (cursor-paginated via the new `/jobs/:id/workitems/:id/logs` endpoint) and indents them under their parent step. Previously only status transitions surfaced; long-running build steps now show progress in real time. GitHub Actions runs wrap the streamed output in a `::group::` block so it collapses by default and surface the public URL via `::notice::` after a successful deploy.
- **`requires.<alias>.env` collision detection**: when a local env file hand-authors a key that the platform injects at runtime from a linked service's credentials (e.g. `DATABASE_URL` written locally while `requires.db.env.url=DATABASE_URL` claims it), `runos deploy` and `apps sync` flag it as informational dead config. Conductor drops the colliding key from `customEnvVars` on every deploy so the runtime value always reflects the linked service; the message points at the cosmetic cleanup.
- **Pre-deploy code drift gate**: `runos deploy` refuses when newer CLI archives exist on the server (someone else deployed via console or CI between this directory's last `apps pull --code` / deploy and now). The check is fail-closed (API failure refuses the deploy) so a fail-open never lets through the very thing the gate exists to prevent. Pass `--force` to override.
- **`runos deploy --force`**: a single bypass flag for both pre-deploy gates (yaml drift and code drift). The diff is shown either way.

### Improvements

- **`apps pull` / `apps diff` correctly read `deployType`**: prior versions conflated provider name with deploy type and stored `github-arc` / `gitlab-runner` as `deployType`, producing perpetual drift on `apps diff` because the server emits `vcs`. Provider identity now flows via the `Integration` block alongside repo/branch metadata; `deployType` carries the canonical `cli` | `vcs` value with `integrationType` as a legacy fallback for older conductors.
- **Class-flap heads-up note on `apps diff`**: when the server stored `resourceRequirementClassId=custom` because cpu/memory/replicas overrides disagree with the named class's defaults (server's `resolveRRC` synthesis), the diff now surfaces a one-line note explaining the mechanic and how to round-trip cleanly. Previously this looked like fresh class drift on every sync.
- **MCP `deploy` tool gains VCS parameters**: `app`, `sha`, `allow_dirty`. Pre-validation stays in the CLI binary (one source of truth for the deployType branching rule) so the MCP shim only translates args. The tool description spells out which flags belong with which deploy type.
- **MCP JSON Schema for object/array fields**: the manifest-driven tool generator now emits `additionalProperties: {type: string}` for `object` fields and `items: {type: string}` for `array` fields. Strict-validating LLM clients (some Anthropic SDK tool wrappers) previously rejected the unannotated schemas. The `object` manifest type now maps to JSON Schema `object` instead of being collapsed to `string`.
- **MCP defensive JSON-string coercion**: when an MCP client ignores the declared field type and sends an `object` / `array` field as a JSON-encoded string (`envVars: '{"K":"v"}'`), the executor now decodes in-place so the wire body matches the manifest's declared type. Conductor previously rejected it as "not an object".
- **`apps pull` pulls both env-var sides independently**: secret env file is gitignored on first pull (created with mode 0600), plain config env file is created with mode 0644 ready to commit. Diff/sync round-trip each side against its corresponding K8s resource.
- **Pre-deploy drift gate validates IDs as defence-in-depth**: app ID and cluster ID from the local yaml are charset-validated via `apps.ValidateIdentifier` before being joined into URLs, so a tampered yaml can't smuggle path components into API requests.
- **Build stamp on local builds**: `make local` now stamps `dev-<utc-timestamp>` into the version string, so dev binaries are version-distinguishable in the wild. Stable releases continue to stamp the git tag.
- **Documentation**: the README and CLAUDE.md gain a deploy-verb section covering the deployType dispatch, the three cluster-id sources (flag → config → yaml), the SHA / dirty-tree gate, and the env-var Secret/ConfigMap split.

### Bug fixes

- **`apps diff` `--redact-secrets` covers the new secret env section**: values in the new `SecretEnv` `SectionDiff` are redacted in the unified-diff output by the same flag that already redacts `.env` content. The MCP `apps_diff` tool keeps passing `--redact-secrets` so secret values never reach the LLM context.

## v1.0.0-rc.1

Foundational release. Introduces IaC workflows for both apps and services, headless authentication for CI/CD, and a topic-driven documentation system for AI assistants. This is a release candidate for testing; install via `https://get.runos.com/cli.sh?release=v1.0.0-rc.1`. The default install URL keeps serving the previous stable.

### New

- **Apps as IaC**: `runos apps pull` / `apps diff` / `apps sync` round-trip an app's full configuration (yaml, env vars, secret files, manifest overrides) between cluster and disk. Pull supports bulk mode (`--all`), single-app mode, code-archive download (`--code` / `--code-version`), drift gates, and section-level diff reports. Sync pushes deltas via dedicated endpoints (PATCH /apps, env-vars, secret-files, overrides, requires).
- **Services as IaC**: `runos services pull` / `services diff` / `services sync` for postgresql, valkey, mysql, and any future service type the manifest exposes. Schema is manifest-driven (zero per-type code in the CLI); a new service type or new settable field on the API side flows through automatically after `runos manifest update`.
- **Service yaml shape is desired-state only**: `runos.service.<cid>.<type>.<sid>.yaml` contains exactly the fields the user can set (`add.Input.Fields ∪ update.Input.Fields ∪ add.Input.Flags`). Audit, derived, and operational fields the show response carries are filtered out automatically. Filename is convention; renames are tolerated via header-based lookup.
- **Apps integration with services IaC**: `apps_pull` cascades into pulling linked service yamls; `apps_sync` refuses `requires:` entries without an `id:` (provisioning is the service-yaml's job); `runos deploy` keeps the `requires.<alias>.class` shorthand and now writes a service yaml on first-time provisioning.
- **PAT-based authentication**: `runos account api-keys add` / `list` / `show` / `update` / `revoke` for managing personal access tokens. The CLI consumes a PAT via `RUNOS_API_KEY` (plus `RUNOS_ACCOUNT_ID`, optional `RUNOS_API_URL`); when set, the CLI bypasses Firebase entirely. Headless CI runners need no `~/.runos/config.json` and no interactive `runos login`.
- **Topic-driven MCP documentation**: the MCP read server now requires the LLM to consume a minimum number of distinct topics (apps, services, api-keys, cicd, ...) before non-topic tools unlock, so AI assistants ground themselves in the workflow before executing it. Topic content is delivered to MCP clients separately from the CLI binary.
- **Service delete guard (409)**: `DELETE /services/<type>/<id>` returns a structured 409 listing dependent apps when any reference the service. The CLI renders this as a multi-line refusal naming each dependent and its alias, with reconcile guidance.
- **`runos follow <jobId>`**: blocking job-status follower with line-oriented output (one line per state change, no escape codes, no spinners, no repaints). Suitable for CI logs and AI consumers; exit code gates downstream pipeline steps.

### Improvements

- **Pre-deploy drift gate**: `runos deploy` refuses when local diverges from server state (yaml or source archive). Pass `--force` to override; the diff is shown either way.
- **Manifest schema tolerance**: `output.fields` now accepts both legacy bare-string entries and the new rich-object shape (`{name, type, description, enum}`). New API-side field metadata flows through without a CLI release.
- **Tarball walker** unconditionally excludes RunOS-managed manifests (`runos*.yaml`, `runos.*/`, `overrides/`, dot-prefixed files) from every deploy archive, regardless of `.dockerignore`. Cross-cluster config can't bleed into a source upload.
- **`apps_pull` writes a default `.dockerignore`** on first pull (skipped when present) covering the same exclusions so external Docker builders honour the same rules.
- **Multi-cluster project shape**: directory-per-app (`runos.<cid>.<id>/` subdirs with `sourceDir: ".."`) is the recommended shape for repos deploying to multiple clusters; `apps_pull` defaults to it and stamps `sourceDir` automatically.

### Renames (breaking since v0.3.9)

- **Env var**: `CONDUCTOR_API_URL` → `RUNOS_API_URL`. Update CI secrets and shell rc files.
- **Config key**: `runos config set conductor-url ...` → `runos config set api-url ...`. Existing on-disk config files keep working unchanged (the internal JSON field is still `conductor_url`).
- **Status output label**: `Conductor:` → `API:` in `runos status`.
- **Topic prose / README**: every reference to the internal codename "conductor" replaced with "RunOS API" or equivalent. Internal Go field names and the `RemoteDomains.Conductor` CDN-config schema kept as-is.

### Internal

- `internal/apps/`: new package backing the apps IaC commands.
- `internal/services/`: new package backing the services IaC commands.
- `internal/auth/resolve.go`: `ResolveToken(cfg)` is the single auth-token entry point; used by every API-touching subcommand.
- `internal/dynacmd/executor.go`: new `ExecuteWithInput` programmatic entry; `*APIError` typed error so callers can branch on status; shared `dispatch` between Execute paths.
- `internal/manifest/types.go`: `Output.Fields` typed as `[]OutputField` with custom Unmarshal/Marshal for forward-compat.
- `internal/jobs/`: `DisplayFollow` (terminal-clear + spinner repaint) replaced by `EmitFollowDeltas(io.Writer, ...)`.
- New direct dep: `github.com/pmezard/go-difflib` (unified-diff output).
- `golang.org/x/term` promoted from indirect to direct.
